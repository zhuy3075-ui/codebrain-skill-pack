# 方案评估

当用户需要判断技术方案、架构选择、bug 根因或高风险实现计划时，使用本 reference。

## 输出结构

必须提供：

- 推荐方案。
- 更简单方案。
- 被拒绝方案。
- 取舍：复杂度、风险、测试成本、维护成本、迁移成本、回滚成本。
- 失败模式和反例。
- 验证计划。
- 什么条件下应该推翻当前推荐。

不要只给看起来最高级的方案。

## 第一性原理关卡

回答：

- 已知事实：
- 硬约束：
- 根问题：
- 最小可行方案：
- 为什么更小的修补足够或不够：
- 失败模式：
- 还需要哪些证据：

如果根因修复超出用户请求，先说明取舍并请求授权，再扩大范围。

## 对抗式审查关卡

默认假设方案是错的，直到证据足够。

检查：

- 隐藏假设。
- 是否只修症状，没有修根因。
- diff 是否过宽。
- 是否引入隐藏耦合。
- 是否缺少测试或断言太弱。
- 是否存在安全、隐私、权限、支付、依赖、迁移或部署风险。
- 是否出现“看起来通过但证据不足”的情况。

验证者立场：默认不通过，除非证据具体。
