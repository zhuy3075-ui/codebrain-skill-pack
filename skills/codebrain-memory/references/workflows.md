# 工作流

会话开始、phase 结束、Loop 执行和写入边界，使用本 reference。

## 语言规则

所有写入 `TASKS.md`、`PHASE_LOG.md`、`HANDOFF.md`、`DECISIONS.md`、`LESSONS.md` 和最终报告的自然语言必须使用简体中文。文件路径、命令、代码标识符、API 名称、固定工具名和错误原文可以保留英文。

## 会话开始

1. 首次使用先获取用户已新建 Obsidian Vault 的完整路径。后续依次解析当前明确路径、当前项目已确认且可访问的路径、`CODEBRAIN_HOME`、已存在的 `~/CODEBRAIN`；明确路径无效或候选冲突时先询问，不静默换目录。仅当用户明确选择不用 Vault 时使用项目内 `docs/codex/<task-slug>/`。
2. 读取 `VAULT_INDEX.md`。
3. 选择或创建 project slug。
4. 读取项目的 `PROJECT_INDEX.md`、`HANDOFF.md`、`TASKS.md` 和最近 `PHASE_LOG.md`。
5. 说明目标、验收标准、非目标、约束和初始验证计划。

如果用户要求实现，且没有关键歧义，给出简短计划后继续执行。

## 编码前

确认：

- 目标和用户可见的成功标准。
- 范围和非目标。
- 相关代码根目录和 read-first 文件。
- 最小可行修复或实现路径。
- 验证命令或人工检查方式。

遇到复杂架构、重复失败、根因调试、迁移或高风险改动时，执行第一性原理关卡：

- 已知事实是什么？
- 硬约束是什么？
- 根问题是什么，而不是表层症状是什么？
- 满足约束的最小方案是什么？
- 更小的表层修补是否足够？如果不足，为什么？
- 还剩哪些失败模式？

## 阶段结束

向 `PHASE_LOG.md` 追加简短条目：

```markdown
## YYYY-MM-DD HH:mm - <阶段标题>

- 目标:
- 读取上下文:
- 决策:
- 涉及文件:
- 验证:
- 下一步:
- 风险:
```

然后更新：

- `HANDOFF.md`：当前状态和接下来三步。
- `TASKS.md`：仅更新真实变化的任务状态。
- `DECISIONS.md`：仅写入已确认决策。
- `LESSONS.md`：仅写入可复用、已验证的经验。

## L1 只报告 Loop

用于 triage、定向和状态刷新。

- 读取最近状态和链接证据。
- 分类为高优先级、观察列表、近期噪音、已阻塞、下一步。
- 只在有用时更新状态文档。
- 不修改业务代码。

## L2 协助修复 Loop

仅在用户明确授权时使用。

1. 每个线程或 worktree 只处理一个小目标。
2. 先复现问题或定义验证方式。
3. 实现最小改动。
4. 运行聚焦验证。
5. 使用独立验证者视角挑刺。
6. 最多三轮审查-修复，超过则升级给用户。

实现者不能自我批准最终验证。如果没有可调用的独立验证者，必须明确标注为模拟验证者审查。

## L3 无人值守 Loop

默认拒绝。

必须得到用户明确批准：

- 预算和时间限制。
- 允许路径和禁止清单。
- 网络、凭据和外部服务权限。
- 回滚计划。
- 日志位置。
- merge、deploy、release、cleanup 的人类检查点。

## 写入边界

默认允许：

- 追加 phase log。
- 更新 handoff 当前状态。
- 更新任务状态。
- 添加已确认决策。
- 添加已验证经验。

需要明确批准：

- 删除或归档 vault 内容。
- 重写知识结构。
- 批量迁移文件。
- 创建自动化或 hooks。
- 启用无人值守执行。

不要把 secrets 或敏感生产数据写入 CODEBRAIN。
